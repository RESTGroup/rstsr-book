# ADR 0007 - Doctest-verified API documentation

## Context

rustdoc doctests have a structural blind spot: they compile and run the
example code but say nothing about the `// output:` comments shown next to
it - pasted output can rot silently while every doctest stays green.
rstsr-book's listings policy had already confronted this (`doc-guide.mdx`:
output "must be real, and must not be given based on guessing"), but the
`doc_draft` tests asserted only values (`rt::allclose`, shape/stride
`assert_eq!`), never the printed string - so displayed output was
trust-based. In AI-generated docs, invented-but-plausible output is the
default failure mode.

## Decision

API docstring examples in `rstsr-core` are verified **twice**:

1. They are real rustdoc doctests executed by `cargo test -p rstsr-core
   --doc` in CI.
2. Each originates from a `tests/doc_draft/` integration test that
   additionally asserts the *printed output string* matches what the
   docstring displays.

The invariant is one-directional: **doc_draft first, docstring second**;
displayed output lines come from the run unchanged; any edit goes through
the doc_draft run again. Policy details: skill `api-doc-conventions`
(`rstsr-agents/skills/api-doc-conventions/SKILL.md`) §5.

## Considered

- **Doctests only** (add `--doc` to CI, skip string assertions) - rejected:
  leaves the displayed-output rot hole open.
- **Extraction sync tests** (a test that parses docstrings and diffs code
  blocks against `doc_draft` anchors) - rejected: verifies the strongest
  property (docstring↔test identity) but is fragile machinery around
  rustdoc's parsing (hidden `#` lines, `compile_fail`/`text` fences) for
  marginal gain over the chosen scheme.
- **Convention only** (keep "paste real output" as an unenforced
  instruction) - rejected: it is what existed, and it did not survive
  contact with AI-generated docs, where invented-but-plausible output is
  the default failure mode.

## Consequences

- The accepted cost is deliberate duplication: an example that shows output
  exists in two places (docstring with hidden setup lines, `doc_draft` with
  assertions), and byte-identity between them is explicitly *not* required
  - the docstring may trim lines. The invariant that matters is the
  one-directional rule above.
- String assertions (`assert_eq!(format!("{result}"), ...)`) are mandatory
  in the twin exactly when the docstring displays that output; hidden
  in-docstring `# assert!` lines remain SHOULD (they verify values in-situ,
  cheaply).
- Future maintainers reading `doc_draft` should not "simplify away" the
  string assertions as redundant with the value asserts - they are the only
  guard on the *displayed text*, which is what users read.
