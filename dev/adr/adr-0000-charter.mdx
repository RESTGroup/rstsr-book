# ADR 0000 - Charter: what an ADR records and how it is shaped

This file is the corpus charter, not a decision record. Unlike the numbered
ADRs it governs, it may be revised at any time as the corpus learns; the true
records (0001+) are persistent once accepted. Lineage: Nygard's original ADR
format and [MADR](https://adr.github.io/madr), adapted to this project.

## What an ADR records

An ADR records an **architectural decision and its rationale** - *what we
decided, and why*, chosen over named alternatives, with the trade-offs it
creates. The decision constrains how code is written going forward.

An ADR is **not** a changelog of completed work, nor a backlog of future
work. Write it for a reader who lacks the original conversation - a new
maintainer, or an agent meeting the design for the first time.

## Canonical shape

Four sections, in this order:

1. **Context** - the situation that forces the decision. **Keep it short**:
   the few facts a reader needs before the decision makes sense. The common
   pitfall is Context bloat - prior code state, extended evidence, and the
   full defense of the choice belong *later* (Considered, Prior state), so
   the essential reading comes first and the expansion follows for the
   reader who needs it.
2. **Decision** - the choice made, stated as a standing rule a reader can
   follow and a reviewer can check against. Multi-part decisions use
   numbered subsections.
3. **Considered** - the named alternatives, each with why it was rejected.
   This is where the extended argument lives; expand freely here.
4. **Consequences** - the structural implications of the decision (what it
   makes easier, harder, or required), positive and negative.

Reading order is the point: front-load. A reader should reach the Decision
early; depth sits behind it, not in front of it.

## Additional sections

An ADR carries at most one or two beyond the canonical four, only when the
content is normative or referential - never as filler:

- **Prior state** - what the code did before the decision, when the delta
  matters. Placed after Consequences.
- **References** - pointers to sources: upstream code, issues, specs.
- **Amendment** - a dated appendix recording a later change to the decision.
- A case-specific section (Discipline, Terminology, Migration boundary, ...)
  when it carries a rule the reader must follow; name it for what it
  governs.

## Persistence and change

True ADRs are persistent, if properly shaped: write the record so it stays
true. When reality shifts, append a dated **Amendment** rather than rewriting
the decision text, or supersede the record with a new ADR that names what it
replaces. Avoid silent rewrites that erase the original reasoning. A record
so heavily amended that it no longer states one rule is two records; split
it.

## Discipline

- **Consequences are implications, not a work log.** "N binaries now compile
  the same body" is a consequence; "we wrote 44 tests" is a changelog entry -
  keep the latter out. Completed metrics and bug fixes belong in the tracking
  artifacts.
- **No `Follow-up` / TODO section.** Future work goes in an issue tracker or
  the relevant tracking file, not the ADR.
- **One decision per ADR.** A change that is itself a decision (e.g. altering
  public API behaviour) gets its own ADR; do not fold it into an unrelated
  one's Consequences.
- Coding-style rules (formatting, naming) belong in `CONTRIBUTING` or
  elsewhere, not here - ADRs sit above style.

## Scope

Write an ADR for a significant, hard-to-reverse design choice: a new test
workflow, a tracking model, a category taxonomy, an ecosystem-wide mechanism.
Do not write one for routine implementation.
